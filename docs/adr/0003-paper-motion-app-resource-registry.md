# paper-motion.app is a resource registry; resources are copied into projects as editable code

Users ask their agent for a video built from resources by name ("use paper-motion.app, backgrounds mesh-sage and grain-slate, effects magic-move and whip-pan"). So every move, background, palette, font pair and recipe is a resource with a name, kept in `registry/<type>/<id>/item.json` in this repo, the single source. `pamo registry build` publishes it as static files for the site and for agents: `registry.json` (index), `r/<id>.json` (one resource, file contents inlined), `llms.txt` and `llms-full.txt`. The site, `apps/web` (Next.js on Vercel), only renders those files plus clips rendered locally by `pamo registry previews`.

Resources install the shadcn way, as code the user owns. `pamo add <id>` copies a move into `moves/`, adds a background to `brand/shader-set/set.json`, merges a palette or a font pair into `brand/tokens.json` and writes a recipe to `pieces/`. It never overwrites a changed file or a different brand value without `--force`. Importing everything by name from the npm package was simpler to update, but agents and users need to change timing, colors and structure freely, and a copy lets them. To keep copies short, the shared helpers live in the engine as `paper-motion/kit`, and each move lives in its own file under `runtime/moves/`. `paper-motion/moves` stays as the index, so existing scenes keep working.

This reverses the v1 spec's "web app out of scope". An MCP server is the next channel; agents that read the web already have everything through `llms.txt` and the JSON files.
